### 📌 작업 개요

LLM 호출 실패(`extract_failed`)가 재실행 캐시에 저장되어 재시도가 영구히 막히던 문제 해결.
구독 세션 한도로 크롤링이 중단될 때마다 `output/raw/`의 해당 파일을 수동으로 지워야 했다.

이슈 #4 작업 과정에서 함께 반영됐고, 회귀 테스트를 추가해 마무리했다.

### 🔍 문제 분석

캐시 쓰기 가드가 `fetch_failed`만 제외하고 `extract_failed`는 정상 결과처럼 저장했다.

`ExtractError`가 나는 경로는 5개인데 그중 4개가 환경 문제다.

| 경로 | 성격 |
|---|---|
| `claude` CLI 없음 / 미로그인 | 환경 |
| 호출 타임아웃 | 일시적 |
| **비정상 종료 — 구독 세션 한도 소진** | 일시적 |
| 응답 envelope 파싱 실패 | 일시적 |
| 스키마 검증 2회 실패 | 콘텐츠 |

마지막 하나만 콘텐츠 관련인데, 그마저도 LLM 응답이 비결정적이라 재시도하면 성공할 수 있다.
즉 다섯 경로 **전부** 캐시할 이유가 없다.

원칙으로 보면 캐시가 저장해도 되는 것은 **그 페이지에 대한 안정적인 사실**이다. `ok`·`mismatch`는
결과를 이미 얻었고 `empty_body`는 본문이 없다는 결정적 사실이다. 반면 `extract_failed`는
재시도하면 결과가 달라질 것을 기대하는 유일한 flag인데 혼자 캐시되고 있었다 —
이미 미캐시로 처리된 `fetch_failed`와 같은 칸에 있어야 할 것이 잘못 분류돼 있었다.

**실제로 두 번 발생했다.** 인스타그램 핸들 수집(이슈 #1) 백필 중 세션 한도로 14건이 굳었고,
검색 탐색(이슈 #4) 백필에서도 같은 일이 반복됐다. 매번 수동 캐시 삭제가 필요했다.

### ✅ 구현 내용

#### 캐시 쓰기 가드에 `extract_failed` 추가

- **파일**: `crawl.py`
- **변경 내용**: 캐시 쓰기 조건을 `record["flag"] not in ("fetch_failed", "extract_failed")`로 변경
- **이유**: 일시적 실패를 영구히 굳히지 않기 위함. `empty_body`·`mismatch`·성공 결과는 계속 캐시

#### 회귀 테스트 추가

- **파일**: `tests/test_crawl.py`
- **변경 내용**: `test_process_row_extract_failed_not_cached` 추가. `extract`가 `ExtractError`를
  던지도록 mock하고, flag가 `extract_failed`이면서 캐시 파일이 생성되지 않음을 검증
- **이유**: 기존에는 `fetch_failed` 쪽만 테스트가 있어 이 가드가 회귀해도 잡히지 않았다

#### 운영 문서 정정

- **파일**: `README.md`
- **변경 내용**: 캐시 동작 절의 "`fetch_failed`는 캐시에 저장되지 않는다"를
  "`fetch_failed`와 `extract_failed`는 캐시에 저장되지 않는다"로 수정
- **이유**: 변경 전 서술이 거짓이 됐다. 운영자가 재실행 동작을 오해할 수 있었다

### 🧭 결정 기록 (ADR)

#### 실패 원인을 분류하지 않고 `extract_failed` 전체를 미캐시 처리

- **문제**: `ExtractError` 5개 경로 중 4개는 일시적이고 1개(스키마 검증 실패)는 콘텐츠 관련인데,
  구분해서 캐시할지 전부 미캐시할지 선택해야 했다
- **선택**: 구분하지 않고 전부 캐시하지 않는다
- **대안**: `ExtractError`에 카테고리를 부여해 콘텐츠 실패만 캐시 — 예외 계층이 늘고 호출부가
  분기를 알아야 한다
- **트레이드오프**: 매번 실패하는 페이지가 있으면 재실행마다 LLM 호출 1건씩 추가로 쓴다.
  21~29행 규모에서는 무시할 만한 비용
- **근거**: 스키마 검증 실패조차 LLM 응답이 비결정적이라 재시도 가치가 있다. 21행 배치에
  예외 분류 체계를 도입하는 것은 과하다

### 📌 참고사항

- **이슈 #4에서 같은 실수 패턴이 신규 코드에 재도입됐다가 최종 리뷰에서 잡혔다.** 탐색이
  세션 한도로 실패하면 `no_candidate`가 캐시에 굳어 재시도가 막히는 문제였고, `discover_cached`가
  실패를 `None`으로 구분해 알리도록 고쳤다. 원인이 같은 만큼 앞으로 캐시 쓰기 지점을 추가할 때는
  "이 상태가 재실행하면 달라질 수 있는가"를 먼저 확인해야 한다
- 이 수정 이전에 생성된 `output/raw/*.json` 중 잘못 저장된 `extract_failed` 캐시는 자동으로
  치유되지 않는다. 해당 파일을 지우고 재실행해야 한다
