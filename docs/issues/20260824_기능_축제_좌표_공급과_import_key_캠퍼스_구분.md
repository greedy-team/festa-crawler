# 🚀 [기능요청] 축제 좌표 공급과 import_key 캠퍼스 구분

## 📝 현재 문제점

- **백엔드 발행 게이트 3종 중 좌표만 공급원이 없다.** 라인업 0건·주최 미연결은 우리 산출물이 채우는데, 좌표는 `festivals.csv`에 컬럼이 없다. 백엔드 `festival` 테이블에 위경도 컬럼이 있고 발행 게이트가 그것을 읽지만 어떤 경로로도 채워지지 않는다
- **결과적으로 임포트로 들어간 축제는 전부 발행 불가다.** 관리자가 개별 발행도 일괄 발행도 할 수 없다. 크롤러가 아무리 잘 수집해도 화면에 안 뜬다
- **좌표는 크롤링으로 얻을 수 없다.** 원천이 블로그 글이고 위경도가 적혀 있지 않다. 사람이 채워야 하는 값이며, 정할 것은 어디에 채우느냐였다
- **`import_key`가 캠퍼스별 개최에서 깨진다.** 현행 `{주최}-{연도}`는 성균관대처럼 한 주최가 캠퍼스별로 축제를 열면 두 축제가 같은 키가 되어 백엔드 UNIQUE 제약을 위반한다. 백엔드 ERD 확정본이 이것을 「열린 질문이 아니라 지금 있는 결함」으로 적고 **결정 소유자를 크롤러 담당자로 지정**해 뒀다 — 키를 만드는 쪽이 정한다
- 시드 `universities-<연도>.csv`에 `campus` 컬럼이 이미 있는데 산출물로도 키로도 나가지 않는다. 읽어서 record에 담기만 하고 버려진다

## 🛠️ 해결 방안 / 제안 기능

**시드를 좌표의 원본으로 삼는다.** 시드는 이미 캠퍼스 단위 행이다 — 한 행 = 한 캠퍼스 = 한 축제. 좌표를 거기 두면 캠퍼스 단위로 자연스럽게 갈리고 백엔드 스키마를 건드릴 일이 없다.

- 시드에 `latitude`·`longitude` 컬럼을 추가하고 29행을 사람이 채운다. 캠퍼스 정문 또는 축제 주무대 기준
- `festivals.csv`가 `venue_name` 뒤에 두 컬럼으로 실어 낸다 (19 → 21)
- **크롤러는 시드 문자열을 그대로 싣는다.** 숫자 변환도 범위 검증도 하지 않는다 — 검증은 백엔드 한 곳이다. 빈 값도 그대로 나가고 발행 게이트가 막는다
- **`import_key`를 `{주최}-{캠퍼스}-{연도}`로 바꾼다** (`연세대학교-신촌캠퍼스-2026`). 키가 시드 행과 1:1이 된다

백엔드 ERD가 적어둔 후보 `{주최}-{연도}-{월}[-{캠퍼스}]`에서 **월은 뺐다.** 그 후보 자신이 「일정이 월을 넘겨 연기되면 키가 바뀌어 임포트가 기존 축제를 못 찾는다」는 약점을 달고 있었다. 캠퍼스는 시드 상수라 흔들리지 않는다.

`host` 테이블에 캠퍼스·좌표를 두는 안도 검토했으나 기각했다. 백엔드 ERD가 `host.sub_name`을 제거하며 「캠퍼스는 주최가 아니라 축제의 속성이다」로 판정한 것을 되돌리게 되고, `host`는 지자체·기업까지 받으려고 일반화한 테이블이라 캠퍼스는 영원히 대학에만 채워지는 컬럼이 된다.

설계 상세는 `2026-08-24-coordinates-and-import-key-design.md`.

## ⚙️ 작업 내용

- 시드 스키마에 좌표 2컬럼 추가 및 29행 입력
- `FESTIVAL_FIELDS`에 2컬럼 추가, `import_key()` 시그니처와 호출부 2곳 변경
- `record` 초기화와 **캐시 히트 갱신 지점**에 좌표 추가. 캐시 히트 경로를 빠뜨리면 기존 캐시로 히트한 대학의 좌표가 빈 값으로 나간다
- **`SCHEMA_VERSION`은 올리지 않는다.** 좌표는 시드에서 오고 LLM 추출 결과는 한 글자도 바뀌지 않는다. 올리면 29곳 재크롤이 아무 소득 없이 발생하고 구독 세션 한도까지 소모한다. 캐시 무효화 결정의 취지는 「추출 결과에 영향을 주는 변경이면 재수집」이고 시드 전용 필드는 이미 캐시 밖에서 갱신되는 구조다
- **시드에 같은 대학이 2행 이상이면 명시적으로 중단하는 가드.** 아래 참고
- 헤더 계약 테스트와 `import_key` 형식 테스트 갱신, 캐시 히트 경로에서 좌표가 채워지는지 검증
- 재실행 후 실측 — 29행 전부 좌표 채워짐, LLM 호출 0건, flag 분포와 라인업 행 수 유지

## ⚠️ 먼저 알아둘 것

**캐시가 대학 이름으로만 갈린다.** 수집·추출 캐시(`raw/{university}.json`), 탐색 후보 캐시(`discovered/{university}.json`), 검수 화면 「다시 돌리기」 전부 그렇다.

가드가 없으면 성균관대 두 캠퍼스가 탐색 후보 캐시를 공유하고, `verify()`는 대학 이름만 대조하므로 캠퍼스를 구분하지 못한다. **같은 축제가 두 import_key로 조용히 두 번 나간다.** 오류가 나지 않고 결과만 틀리는 종류이며 이 저장소가 이미 두 번 겪은 유형이다.

캐시 키를 캠퍼스 단위로 바꾸는 것은 이번 범위 밖이다 — 파일명 규칙이 바뀌어 기존 캐시 29개가 전부 미스가 되고, 위치 변경은 감지·안내를 동반해야 한다. 다캠퍼스가 실제로 필요해질 때 그 비용을 치른다.

**음수 좌표는 `_sanitize_cell`에 걸린다.** `-`로 시작하는 값 앞에 작은따옴표가 붙는다(Excel 수식 인젝션 가드). 국내 좌표는 위도·경도 모두 양수라 지금은 안 걸리지만 **국내 한정이라는 전제** 위에 있다.

## ⚠️ 선행 조건 · 범위 밖

- **백엔드 짝 이슈와 동시에 나가야 한다.** 헤더가 순서까지 정확 일치 계약이라 한쪽만 바뀌면 업로드가 전부 막힌다. **배포 순서는 백엔드 먼저** — 우리는 손으로 돌리는 로컬 배치라 백엔드가 새 헤더를 받게 된 뒤 실행하면 사이에 창이 없다
- **전 29행의 `import_key`가 바뀐다.** 백엔드에 운영 데이터가 아직 없어 지금은 비용이 없지만, 개발 서버에 시험 임포트한 축제가 있으면 비우고 시작해야 한다
- `address`는 넣지 않는다. 발행을 막지 않고 「주소 복사」 UI 존재 여부가 미확인이다
- 수동 입력(붙여넣기) 경로는 별건이다. 백엔드가 `discovery=PASTED`를 이미 허용하고 있으나 우리 쪽에 그 명령이 없다
- `name`에서 주최명을 떼는 주체는 여전히 미정이다
